    Part 4c: Permissions (permissions.js & requirePermission.js)

    src/constants/permissions.js

    This file defines all available permission keys in the system and the default roles (admin and member) that are assigned at signup. It serves as a single source of truth for permission management.

    export const PERMISSIONS = Object.freeze({
  // Projects
  PROJECT_CREATE: 'project:create',
  PROJECT_READ:   'project:read',
  PROJECT_UPDATE: 'project:update',
  PROJECT_DELETE: 'project:delete',

  // Tasks
  TASK_CREATE:    'task:create',
  TASK_READ:      'task:read',
  TASK_UPDATE:    'task:update',
  TASK_DELETE:    'task:delete',

  // User management
  USER_INVITE:    'user:invite',
  USER_MANAGE:    'user:manage',

  // Billing
  BILLING_VIEW:   'billing:view',
  BILLING_MANAGE: 'billing:manage',
});

export const ALL_PERMISSIONS = Object.values(PERMISSIONS);

/**
 * Default role → permission mappings used at signup.
 * "admin" gets every permission; "member" gets basic read/task access.
 * Custom roles can later hold any subset of ALL_PERMISSIONS.
 */
export const DEFAULT_ROLES = Object.freeze({
  admin: [...ALL_PERMISSIONS],
  member: [
    PERMISSIONS.PROJECT_READ,
    PERMISSIONS.TASK_CREATE,
    PERMISSIONS.TASK_READ,
    PERMISSIONS.TASK_UPDATE,
  ],
});

export default PERMISSIONS;

    Explanation of src/constants/permissions.js:

    • PERMISSIONS: An Object.freeze()d object containing all distinct permission keys. Each key is a string in the format 'resource:action' (e.g., 'project:create', 'task:read'). This centralizes permission definitions, making them discoverable and ensuring consistency across the application.
    • ALL_PERMISSIONS: An array derived from Object.values(PERMISSIONS), providing a complete list of all permission keys in the system.
    • DEFAULT_ROLES: An Object.freeze()d object defining the permissions associated with the default roles, admin and member, used during user signup.
      • admin: Is granted all available permissions (ALL_PERMISSIONS).
      • member: Is granted a subset of permissions necessary for basic project and task management (e.g., PROJECT_READ, TASK_CREATE, TASK_READ, TASK_UPDATE).
      This structure allows for easy expansion with custom roles later, which can hold any combination of ALL_PERMISSIONS.

    src/middleware/requirePermission.js

    This middleware provides functions to enforce role-based access control (RBAC) on routes. It ensures that the authenticated user has the necessary permissions to perform an action.

    import { ALL_PERMISSIONS } from '../constants/permissions.js';
import AppError from '../utils/AppError.js';

/**
 * Validate that every key is a known permission.
 * Called at module load time (server start) when the middleware is configured,
 * so typos like 'projct:delete' are caught immediately, not when a user hits the route.
 */
const validateKeys = (keys) => {
  for (const key of keys) {
    if (!ALL_PERMISSIONS.includes(key)) {
      throw new Error(`Unknown permission key: ${key}`);
    }
  }
};

/**
 * requirePermission(...keys) middleware.
 *
 * Allows the request only if req.user.permissions contains ALL of the given keys.
 * Must be used after protect.js. If req.user is missing, returns 401.
 * If a permission is missing, returns 403 with message "Forbidden".
 * Unknown permission keys throw at startup (when the middleware is configured),
 * not when a user hits the route.
 */
const requirePermission = (...keys) => {
  validateKeys(keys);
  return (req, _res, next) => {
    if (!req.user) {
      return next(new AppError('Unauthorized', 401));
    }
    const missing = keys.filter((key) => !req.user.permissions.includes(key));
    if (missing.length > 0) {
      return next(new AppError('Forbidden', 403));
    }
    next();
  };
};

/**
 * requireAnyPermission(...keys) middleware.
 *
 * Allows the request if at least one of the given keys matches a permission
 * in req.user.permissions. If none match, returns 403 with message "Forbidden".
 * Must be used after protect.js. If req.user is missing, returns 401.
 * Unknown permission keys throw at startup.
 */
const requireAnyPermission = (...keys) => {
  validateKeys(keys);
  return (req, _res, next) => {
    if (!req.user) {
      return next(new AppError('Unauthorized', 401));
    }
    const hasAny = keys.some((key) => req.user.permissions.includes(key));
    if (!hasAny) {
      return next(new AppError('Forbidden', 403));
    }
    next();
  };
};

// Trade-off explanation:
// Permissions are baked into the JWT access token at issuance.
// A role change in the database does NOT immediately update existing tokens.
// The new role permissions take effect only after the user's next token refresh
// (up to 15 minutes, the access token expiry). This is intentional for Phase 2;
// a revocation list can be added later if immediate role changes are needed.

export { requirePermission, requireAnyPermission };

    Explanation of src/middleware/requirePermission.js:

    • Module-load time validation of permission keys: The validateKeys function is called immediately when the module is loaded (i.e., when the server starts). This function iterates through all provided permission keys and checks if they exist in the ALL_PERMISSIONS list from permissions.js. If an unknown key is found, it throws an error, effectively catching typos or undefined permissions at server startup rather than at runtime when a user hits a specific route. This prevents silent failures and makes debugging easier.
    • requirePermission(...keys): This middleware function takes a variable number of permission keys as arguments. It checks if the authenticated user (req.user.permissions, populated by protect.js) possesses all of the specified permissions. If any permission is missing, it returns a 403 Forbidden error. If req.user is not present (meaning the request wasn't authenticated), it returns a 401 Unauthorized error.
    • requireAnyPermission(...keys): Similar to requirePermission, this middleware also takes a variable number of permission keys. However, it only requires the user to have at least one of the specified permissions. If the user has none of the required permissions, it returns a 403 Forbidden error. If req.user is not present, it returns a 401 Unauthorized error.
    • Trade-off: Permissions are embedded directly in the JWT access token. This means that if a user's role or permissions are changed in the database, these changes will not take effect immediately. They will only be reflected after the user's current access token expires (typically 15 minutes) and a new one is issued. This design choice prioritizes performance by avoiding a database lookup on every request, with the understanding that immediate permission updates are not a critical requirement for Phase 2 of this project. A revocation list could be implemented later if real-time permission updates become necessary.
