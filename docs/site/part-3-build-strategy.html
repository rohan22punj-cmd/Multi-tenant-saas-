Multi-Tenant SaaS Walkthrough

    Part 3: The 12 Build Steps

    BUILT

    This is the story of how we actually built the Multi-Tenant backend, step-by-step. Each step was chosen to solve a specific problem before we moved on to the next dependency.

    1. The Foundation

    Files: src/server.js, src/app.js, src/config/*, src/utils/AppError.js, src/middleware/errorHandler.js

    Problem: Need a clean base to hang middleware and routes on without leaking test code into production runtime.

    How: Separate Express app setup (app.js) from server listening (server.js). Tests import app.js directly. Custom error handling ensures we never leak raw error stack traces to clients.

    2. Signup

    Files: src/services/authService.js, src/controllers/authController.js

    Problem: How to bootstrap a tenant and an admin user simultaneously?

    How: We generate a URL-safe slug from the company name, create the tenant, then inside that tenant's context, create an "admin" role and the first user.

    3. Rate Limiting & Structured Logging

    Files: src/middleware/rateLimiter.js, src/utils/requestId.js, src/utils/requestLogger.js

    Problem: APIs are easily abused. Without logging, production debugging is blind.

    How: Every request is tagged with a UUID (requestId). Logs include this ID for correlation. Rate limiters prevent brute force attacks on auth routes.

    4. Login with companySlug

    Files: src/services/authService.js (login)

    Problem: Multi-tenant logins need more than just email/password—they need to know which company you belong to.

    How: We first find the tenant by companySlug, then use that tenantId to scope the user query. This protects against user enumeration.

    5. Refresh & Logout

    Files: src/services/authService.js (refresh, logout)

    Problem: JWTs must expire. Refreshing tokens securely requires preventing replay attacks.

    How: Refresh token rotation. If an old token is used, we detect reuse and invalidate all sessions for that user instantly.

    6. Auth Middleware & Tenant Context

    Files: src/middleware/protect.js, src/utils/tenantContext.js

    Problem: How to pass "which tenant is this?" down into database queries without passing tenantId through every function argument?

    How: We use AsyncLocalStorage. tenantContextMiddleware sets the tenant on every request; tenantPlugin reads this and forces it into every Mongoose query.

    7. Tenant Plugin

    Files: src/plugins/tenantPlugin.js

    Problem: Developer error. It is incredibly easy to forget to add tenantId: req.user.tenantId to a findOne() query.

    How: We intercept every Mongoose query and automatically inject the tenant restriction. It's impossible to "forget."

    8. Permission Middleware

    Files: src/middleware/requirePermission.js, src/constants/permissions.js

    Problem: Simple "is logged in" isn't enough. We need "can this user create projects?"

    How: We cache user permissions in their access token payload. Middleware checks this list before calling the route handler.

    9. Invite Users

    Files: src/controllers/authController.js (invite, acceptInvite)

    Problem: How to add members to a tenant without them signing up through the company landing page?

    How: Admins invite users via email; users accept with a one-time token that links their new account to the tenant.

    10. User Management

    Files: src/controllers/userController.js

    Problem: Users need to be deactivated (fired/left company) or have roles changed.

    How: CRUD operations on User model, scoped by tenantId. Deactivation sets isActive: false, preventing login.

    11. Business Logic

    Files: src/services/projectService.js, src/services/taskService.js, src/services/planService.js, src/services/activityService.js

    Problem: The actual application logic—managing projects and tasks—while enforcing plan limits (e.g., max 5 projects).

    How: Services perform the business logic and check the planService to verify the tenant isn't over their subscription limit before performing writes.

    12. Billing

    Status: PLANNED

    We have designed the integration with Stripe, but it remains to be built.
