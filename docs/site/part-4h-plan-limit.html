    Part 4h: Plan Limit & Atomic Reservation (planService.js)

    What this covers: How the system enforces plan limits (e.g., max 3 projects on Free) using an atomic counter on the Tenant document. The plan is read from the database on every check — not from the JWT — so upgrades/downgrades take effect immediately.

    Why Not Count Projects?

    The naive approach — countDocuments then create — fails under concurrency:

    1. Request A counts 2 projects
    2. Request B counts 2 projects
    3. Both decide "under limit"
    4. Both create → tenant has 4 projects (limit was 3)

    Atomic Conditional Update

    Instead, we keep a projectCount field on the Tenant and reserve a slot with ONE atomic operation. MongoDB serializes updates to a single document, so only one concurrent request can increment the counter.

    Source: src/services/planService.js

    // src/services/planService.js (lines 55-81)

export async function reserveProjectSlot(tenantId) {
  const tenant = await getTenantPlan(tenantId);
  const limit = getPlanLimits(tenant.plan).maxProjects;

  // Pro (or any unlimited plan): always allowed, but still count for
  // accurate accounting in case the tenant later downgrades.
  if (limit === Infinity) {
    await Tenant.findByIdAndUpdate(tenantId, { $inc: { projectCount: 1 } });
    return { reserved: true, limit, plan: tenant.plan };
  }

  const updated = await Tenant.findOneAndUpdate(
    { _id: tenantId, projectCount: { $lt: limit } },
    { $inc: { projectCount: 1 } },
    { new: true }
  );

  if (updated) {
    return { reserved: true, limit, plan: tenant.plan };
  }

  // The conditional update matched nothing: the counter is already at the
  // limit. Exactly one concurrent request can win the update above, so we
  // reject without recounting (see the header for why a recount-and-retry
  // would be wrong here).
  return { reserved: false, limit, plan: tenant.plan };
}

    Why No Recount-and-Retry?

    If the conditional update fails, we do not re-count projects and try again. Here's why:

    • The counter is at the limit because another request already reserved the slot but hasn't inserted its project yet
    • A recount would see projectCount === limit and (wrongly) think it can proceed
    • That would hand out the same slot twice, breaking the guarantee

    Drift is avoided by always releasing the slot on every failure path (see releaseProjectSlot callers). A client that races and loses simply retries after the winner commits.

    Reading the Plan from the Database

    getTenantPlan reads the Tenant document on every check, not from the JWT.

    // src/services/planService.js (lines 41-47)

export async function getTenantPlan(tenantId) {
  const tenant = await Tenant.findById(tenantId).lean();
  if (!tenant) {
    throw new AppError('Tenant not found', 404);
  }
  return tenant;
}
    Why? Access tokens live for 15 minutes and bake in the plan at issuance time. If we trusted the token, a company that upgraded in Stripe would keep the old limits until they re-logged in. Reading the Tenant row makes plan changes take effect immediately.

    Releasing a Slot

    When a project is archived, deleted, or a create fails after reservation, the slot is returned:

    // src/services/planService.js (lines 88-93)

export async function releaseProjectSlot(tenantId) {
  await Tenant.updateOne(
    { _id: tenantId, projectCount: { $gt: 0 } },
    { $inc: { projectCount: -1 } }
  );
}

    The $gt: 0 guard prevents the counter from going negative if releases ever double-fire.

    Compensation in projectService.js

    If Project.create throws after a slot was reserved, we release it:

    // src/services/projectService.js (lines 48-66)

const tenantId = getTenantId();
const slot = await reserveProjectSlot(tenantId);

if (!slot.reserved) {
  return { limitReached: true, limit: slot.limit, plan: slot.plan };
}

let project;
try {
  project = await Project.create({
    name,
    description: body.description,
    createdBy: actorId,
  });
} catch (err) {
  // Compensate: we reserved a slot but created nothing, so hand it back.
  await releaseProjectSlot(tenantId);
  throw err;
}

    Similarly, updateProject (un-archiving) and deleteProject call releaseProjectSlot on their failure paths and when archiving/deleting active projects.
