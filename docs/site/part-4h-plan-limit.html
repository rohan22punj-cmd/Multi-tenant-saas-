Plan Limit & Atomic Reservation

We enforce plan limits (like project counts) by reading the plan directly from the database to ensure immediate enforcement when a company upgrades or downgrades.

Atomic Reservation

To avoid race conditions where concurrent requests exceed the limit, we use an atomic conditional update in src/services/planService.js.

// src/services/planService.js

const updated = await Tenant.findOneAndUpdate(
  { _id: tenantId, projectCount: { $lt: limit } },
  { $inc: { projectCount: 1 } },
  { new: true }
);

Handling Failures

Because the update is atomic, we reject the request immediately if it fails (no recount-and-retry is needed, as it would cause double-issuance of slots). projectService.js handles compensation if a project creation fails.

// src/services/projectService.js

try {
  project = await Project.create({ ... });
} catch (err) {
  // Compensate: release the slot back
  await releaseProjectSlot(tenantId);
  throw err;
}
