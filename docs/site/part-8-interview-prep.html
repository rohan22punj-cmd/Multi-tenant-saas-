Important security features include refresh token hashing and rotation to prevent session hijacking, and a dummy bcrypt compare in login to prevent timing attacks and user enumeration. This project also features race-safe plan limits using atomic database operations and structured logging for auditability. Stripe billing is designed, but not yet built, with a robust webhook idempotency strategy in mind. The hard parts were ensuring tenant isolation across all Mongoose operations, managing concurrent access for plan limits, and designing a secure authentication flow that is both robust and performant. This project showcases how to build a scalable and secure foundation for any SaaS application."

    4. Trade-offs I Made and Would Explain

    Being able to articulate trade-offs is a sign of a senior engineer.

    • Shared Database with `tenantId`:

      Trade-off: Lower cost and simpler deployments than database-per-tenant, but increases the risk of data leaks if tenant filtering fails. This project mitigates this by enforcing `tenantId` at the Mongoose plugin level (data layer) for all operations, making it extremely hard to bypass. It's suitable for most SaaS companies, especially early-stage ones, but highly regulated industries might prefer physical separation.

    • 15-minute Token Window (after deactivation/role change):

      Trade-off: For performance, access tokens are stateless and not checked against the database on every request. This means a deactivated user or one with a demoted role might retain their old permissions for up to 15 minutes (the token's expiry). This was an acceptable trade-off for a simple project to avoid the complexity of a real-time revocation list (e.g., Redis blocklist), which would add a database call to every protected request.

      src/middleware/protect.js
      import { verifyAccessToken } from '../utils/tokens.js';
import AppError from '../utils/AppError.js';
import { runWithTenant } from '../utils/tenantContext.js';

const UNAUTHORIZED = 'Unauthorized';

const protect = async (req, _res, next) => {
  const authHeader = req.headers.authorization;
  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    throw new AppError(UNAUTHORIZED, 401);
  }

  const token = authHeader.split(' ')[1];

  let decoded;
  try {
    decoded = verifyAccessToken(token);
  } catch {
    throw new AppError(UNAUTHORIZED, 401);
  }

  req.user = {
    userId: decoded.userId,
    tenantId: decoded.tenantId,
    roleId: decoded.roleId,
    permissions: decoded.permissions || [],
  };

  runWithTenant(
    { tenantId: decoded.tenantId, userId: decoded.userId },
    () => next()
  );
};

export default protect;

      Fix for a bigger company: Implement a Redis-backed token blocklist. When a user is deactivated or their role changes, their `jti` (JWT ID) from the access token is added to Redis with the access token's remaining expiry. The `protect.js` middleware would then check this blocklist on every request, providing near-instant revocation.

    • Hashed Refresh Tokens (in DB):

      Trade-off: Storing hashes instead of raw refresh tokens protects against database breaches, as attackers cannot reverse the hashes into usable tokens. This is a strong security posture. The cost is slightly increased complexity in the authentication service for hashing and comparing.

    • Redis plus Database Unique Index (PLANNED for Webhook Idempotency):

      Trade-off: This is a belt-and-suspenders approach to idempotency. Redis provides a fast, temporary claim (`SET NX EX`) to prevent immediate duplicates and handle retry logic (release key on error). The database unique index on `eventId` (StripeEvent collection) provides a durable, transactional backup for long-term exactly-once processing, even if Redis is down or data is lost. It adds complexity but guarantees reliability for critical financial operations.
