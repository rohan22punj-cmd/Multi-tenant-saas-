Multi-Tenant SaaS Walkthrough

    Part 6: How It Can Still Break — Isolation Gaps & Weak Spots

    This page documents known limitations. The tenant plugin provides strong isolation for standard Mongoose operations, but several gaps exist. Every item here is a real issue in the current codebase — not hypothetical.

    1. Mongoose aggregate with $lookup and $unionWith — Cross-Collection Joins Are NOT Scoped

    The tenantPlugin injects a $match: { tenantId } stage at the start of the pipeline. However, $lookup and $unionWith stages execute independently and are NOT automatically scoped by the plugin on the target model.

    The Problem

    // This aggregation runs inside Company A's context
const results = await Project.aggregate([
  { $match: { status: 'active' } },  // ← plugin injects { tenantId: "A" } HERE
  {
    $lookup: {
      from: 'tasks',         // ← Tasks collection
      localField: '_id',
      foreignField: 'projectId',
      as: 'tasks'
    }
  }
]);

// The $lookup reads from the ENTIRE tasks collection — it does NOT
// automatically filter to tenantId: "A". Company A sees Company B's tasks
// that happen to reference Company A's project IDs (if IDs were predictable).

    Why This Happens

    // src/plugins/tenantPlugin.js (lines 206-213)

schema.pre('aggregate', async function () {
  if (isUnscoped()) return;
  const tenantId = getTenantId();
  const pipeline = this.pipeline();
  injectAggregateMatch(pipeline, tenantId);  // Only injects at position 0
});

// injectAggregateMatch (lines 125-146) only prepends $match.
// It does NOT recurse into $lookup/$unionWith sub-pipelines.

    Fix Options

    1. Manual $match inside $lookup pipeline: Add { $match: { tenantId: getTenantId() } } as the first stage of every $lookup pipeline.
    2. Use runUnscoped with explicit filtering: For complex cross-collection queries, run unscoped and manually filter both collections.
    3. Plugin enhancement (future): Recursively walk the pipeline and inject tenant filters into $lookup/$unionWith sub-pipelines.

    Risk: If project IDs are predictable (sequential ObjectIds), Company A could craft an aggregation that joins into Company B's tasks. Current mitigation: ObjectIds are random enough that this is hard to exploit, but it's a real isolation gap.

    2. Direct MongoDB Driver Calls Bypass Mongoose Middleware Completely

    Any code that uses Model.collection.find(), Model.collection.insertOne(), or mongoose.connection.db bypasses the tenant plugin entirely.

    Examples of Bypass

    // ALL OF THESE BYPASS THE TENANT PLUGIN:

// 1. Direct collection access
await User.collection.find({}).toArray();  // Returns ALL tenants' users

// 2. Raw MongoDB driver
const db = mongoose.connection.db;
await db.collection('users').find({}).toArray();  // No tenant filter

// 3. Bulk operations on collection
await Project.collection.bulkWrite([
  { insertOne: { document: { name: 'Hacked', tenantId: 'tenant-B' } } }
]);  // No tenant check on insert

// 4. Raw aggregation
await mongoose.connection.db.collection('projects').aggregate([...]).toArray();

    Where This Could Happen Accidentally

    • Performance optimization attempts ("Mongoose is slow, let me use the raw driver")
    • Migration scripts that forget to wrap in runUnscoped
    • Third-party libraries that accept a Mongoose model and use model.collection internally
    • Debugging code left in production

    Fix

    Enforce a lint rule or code review policy: Never use .collection or mongoose.connection.db directly. If you need raw access, use runUnscoped('explicit reason', callback) so the audit trail exists.

    3. bulkWrite Throws Explicit Error — Forces runUnscoped()

    The tenant plugin intentionally throws on bulkWrite because it cannot safely auto-scope arbitrary operations.

    The Code

    // src/plugins/tenantPlugin.js (lines 279-294)

schema.pre('bulkWrite', async function () {
  if (isUnscoped()) return;
  throw new Error(
    'bulkWrite() is not supported on tenant-scoped models. ' +
    'It accepts arbitrary operations that cannot be safely auto-scoped. ' +
    'Use runUnscoped(reason, callback) with a valid justification if absolutely necessary.'
  );
});

    Why This Exists

    bulkWrite accepts an array of mixed operations (insertOne, updateOne, deleteOne, replaceOne), each with their own filter and update documents. Intercepting and rewriting every operation safely is complex and error-prone.

    The Risk

    Developers forced to use runUnscoped for bulk operations might accidentally widen the scope too far. The required reason string creates an audit trail, but human error is still possible.

    // Developer must do this (and it's easy to get wrong):
await runUnscoped('migration: backfill project slugs', async () => {
  await Project.bulkWrite([
    { updateOne: { filter: { _id: id1 }, update: { $set: { slug: 'new-slug' } } } },
    { updateOne: { filter: { _id: id2 }, update: { $set: { slug: 'other-slug' } } } },
  ]);
});

    4. estimatedDocumentCount() Throws Explicit Error — Forces countDocuments()

    The Code

    // src/plugins/tenantPlugin.js (lines 193-201)

schema.pre('estimatedDocumentCount', async function () {
  if (isUnscoped()) return;
  throw new Error(
    'estimatedDocumentCount() cannot be filtered by tenant and is disabled on tenant-scoped models. ' +
    'Use countDocuments() instead, or wrap in runUnscoped() with a valid reason.'
  );
});

    Why

    estimatedDocumentCount() uses collection metadata (fast, approximate) and cannot accept a query filter. It would return the total count across ALL tenants — a massive data leak if allowed.

    Safe Alternative

    // SLOW but safe — uses query filter (tenant plugin injects tenantId)
const count = await Project.countDocuments({ status: 'active' });

// FAST but requires explicit justification
const total = await runUnscoped('analytics: total project count across all tenants', async () => {
  return Project.estimatedDocumentCount();
});

    5. The 15-Minute Access Token Window — Deactivated/Demoted Users Retain Access

    Access tokens are stateless JWTs. When a user is deactivated or demoted, their existing access token remains valid for up to 15 minutes (the token expiry).

    The Code (protect.js)

    // src/middleware/protect.js (lines 9-13)

/**
 * 3. Takes userId, tenantId, roleId, permissions directly from the
 *    token payload — NO database call. This is fast (no extra round-
 *    trip) but means a deactivated user keeps access for up to
 *    15 minutes until the token expires. That trade-off is intentional
 *    for Phase 2; we can add a revocation list later if needed.
 */

    The Code (requirePermission.js)

    // src/middleware/requirePermission.js (lines 62-67)

// Trade-off explanation:
// Permissions are baked into the JWT access token at issuance.
// A role change in the database does NOT immediately update existing tokens.
// The new role permissions take effect only after the user's next token refresh
// (up to 15 minutes, the access token expiry). This is intentional for Phase 2;
// a revocation list can be added later if immediate role changes are needed.

    Real-World Impact

    ScenarioWhat HappensDuration
    Admin deactivates userUser's access token still worksUp to 15 min
    Admin demotes user (admin → member)User keeps admin permissionsUp to 15 min
    User's role permissions changedOld permissions still workUp to 15 min
    Refresh token usedNew access token has correct permissionsImmediate

    Why This Trade-off?

    • Performance: No DB lookup on every request. protect.js is pure JWT verification — sub-millisecond.
    • Scalability: Stateless auth works horizontally without shared session store.
    • Simplicity: No Redis dependency for core auth path.

    Fix: Redis Token Blocklist in protect.js

    // PLANNED — add to protect.js

import redis from '../config/redis.js';

const protect = async (req, _res, next) => {
  // ... existing token extraction & verification ...

  // NEW: Check Redis blocklist
  const isBlocked = await redis.exists(`token:block:${decoded.jti}`);
  if (isBlocked) {
    throw new AppError('Token revoked', 401);
  }

  req.user = { ... };
  runWithTenant({ tenantId: decoded.tenantId, userId: decoded.userId }, () => next());
};

// When deactivating/demoting a user:
await redis.set(`token:block:${user.jti}`, 'revoked', 'EX', 900);  // 15 min TTL

    Requires adding jti (JWT ID) to access tokens at issuance. The blocklist key expires at the same time the token would, so no manual cleanup needed.

    6. Multi-Process Lock Limitation — withTenantLock Is In-Memory Per Node Process

    The withTenantLock function in userController.js serializes role changes and deactivations only within a single Node.js process.

    The Code

    // src/controllers/userController.js (lines 44-71)

/**
 * Per-tenant in-process mutex.
 *
 * LIMIT: this only serializes requests handled by this Node process. If the
 * API runs on several instances, replace it with a distributed lock (Redis
 * SET NX / MongoDB lease) — the call sites stay the same.
 */
const tenantLocks = new Map();

function withTenantLock(tenantId, task) {
  const key = String(tenantId);
  const previous = tenantLocks.get(key) || Promise.resolve();
  const run = previous.then(() => task());

  const tail = run.catch(() => {});
  tenantLocks.set(key, tail);
  tail.then(() => {
    if (tenantLocks.get(key) === tail) tenantLocks.delete(key);
  });

  return run;
}

    Why This Exists

    The "last admin" checks in deactivate and changeRole are read-check-then-write sequences. Without serialization, two admins could simultaneously demote each other, both seeing "one other admin remains," and the company ends up with zero admins.

    The Gap

    // Scenario: Two API instances behind a load balancer

// Instance 1 receives: Admin A demotes Admin B
// Instance 2 receives: Admin B demotes Admin A

// Both instances have their OWN tenantLocks Map.
// Both pass the "remaining admin count" check.
// Both writes succeed.
// Result: ZERO active admins in the company.

    Fix: Distributed Lock via Redis SET NX

    // PLANNED — replace withTenantLock implementation

import redis from '../config/redis.js';

async function withTenantLock(tenantId, task) {
  const lockKey = `lock:tenant:${tenantId}`;
  const lockValue = `${process.pid}-${Date.now()}-${Math.random()}`;

  // Try to acquire lock (10 second TTL)
  const acquired = await redis.set(lockKey, lockValue, 'NX', 'EX', 10);

  if (!acquired) {
    // Wait and retry (simple backoff)
    await new Promise(r => setTimeout(r, 50));
    return withTenantLock(tenantId, task);
  }

  try {
    return await task();
  } finally {
    // Release lock only if we still own it (Lua script for atomicity)
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
      else
        return 0
      end
    `;
    await redis.eval(script, 1, lockKey, lockValue);
  }
}

    7. Unbuilt / PLANNED Items — Not Tested, Not Protected

    The following features are designed but not implemented. They have NO tests, NO isolation guarantees, and NO code in the repo.

    FeatureStatusIsolation Risk
    Stripe Billing / Webhooks PLANNED Webhook handler must verify tenant from Stripe customer metadata; plan sync must use runUnscoped for Tenant model
    Email Invites PLANNED Invite tokens must be scoped to tenant; acceptance flow must verify companySlug matches token
    Frontend Application PLANNED No API enforcement — frontend must not send tenantId in requests (backend ignores it anyway)
    Custom Roles PLANNED Role CRUD must enforce tenant isolation; permission validation must prevent privilege escalation
    Audit Log Export PLANNED Export endpoint must require user:manage and run scoped; runUnscoped only for super-admin

    When these are built, they must follow the same patterns: protect → requirePermission → tenant-scoped service calls. Any runUnscoped usage must have a logged reason.
