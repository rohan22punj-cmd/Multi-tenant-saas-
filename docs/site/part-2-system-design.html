    The Tenancy Decision

    Three ways to isolate tenants in a database:

    ApproachIsolation StrengthCostComplexityWhen It Wins
    Database per tenant Maximum — physically separate High High Regulated industries, huge tenants
    Schema per tenant Strong — separate tables Medium Medium PostgreSQL, moderate scale
    Shared DB + tenantId (this project) Code-enforced — single table, filtered queries Low Low Startups, small teams, portfolio projects

    Risk accepted: A bug in the tenant filter could leak data. That's why the entire security model revolves around tenantId coming only from the verified JWT, never from the request body, params, or query.

    Six Design Rules

    1. tenantId only from JWT — src/middleware/protect.js decodes the token and puts tenantId in AsyncLocalStorage. No controller reads it from req.body, req.params, or req.query.
    2. Isolation in the data layer — src/plugins/tenantPlugin.js hooks every Mongoose query. Controllers never add tenantId manually.
    3. Permissions by key, never role name — Roles store arrays of permission strings (project:create, etc.). Code checks requirePermission('project:create'). Role names can change; permission keys don't.
    4. Refresh tokens and invite tokens stored only as hashes — SHA-256 before save. If the DB leaks, attackers get useless hashes.
    5. Every login-style failure returns identical generic message — "Invalid credentials" for wrong password, wrong company, inactive user, missing user. No enumeration.
    6. Webhooks claimed exactly once — Redis SET NX EX on event ID. If processing fails, delete the key so Stripe retries.

    Data Model

    Every collection has tenantId as the first key in its compound indexes — this makes the tenant filter hit an index prefix.

    CollectionKey FieldsIndexes
    Tenant name, slug, plan, stripeCustomerId (PLANNED), stripeSubscriptionId (PLANNED), subscriptionStatus (PLANNED), currentPeriodEnd (PLANNED), projectCount unique slug
    User name, email, passwordHash, roleId, isActive, refreshTokenHash unique (tenantId, email)
    Role name, permissions[], isSystemRole unique (tenantId, name)
    Invite email, roleId, invitedBy, tokenHash, expiresAt, acceptedAt tokenHash
    Project name, description, isArchived, createdBy (tenantId, createdAt)
    Task projectId, title, description, status, assigneeId, createdBy, dueDate, position (tenantId, projectId, status), (tenantId, assigneeId)
    ActivityLog actorId, action, entityType, entityId, meta (tenantId, createdAt)
    StripeEvent (PLANNED) eventId, type, tenantId, processedAt unique eventId

    Middleware Chain (per request)

    1. requestId — UUID for tracing
    2. helmet — security headers
    3. cors — cross-origin
    4. express.json — body parsing
    5. requestLogger — structured log after response
    6. rate limiters — per-IP caps
    7. protect — JWT verify → set AsyncLocalStorage tenant context
    8. requirePermission — check permission key in JWT
    9. Controller — thin handler, no tenant logic
    10. errorHandler — central error formatting
