4d Login Service & Timing Attack Protection

This page explains the login() function within src/services/authService.js, focusing on how it handles user authentication, company lookup, user lookup within tenant context, and crucial security measures like timing attack protection and generic error messages.

login() function in src/services/authService.js

The login function is responsible for authenticating an existing user based on their company slug, email, and password. It employs several security practices to prevent enumeration attacks and ensure data integrity.

Source: src/services/authService.js

export async function login({ companySlug, email, password }) {
  // 1. Find the tenant (unscoped - Tenant model has no tenantId)
  const tenant = await runUnscoped(
    'login: find tenant by slug',
    () => Tenant.findOne({ slug: companySlug })
  );

  // 2. Find the user within that tenant INSIDE tenant context
  // Context is set manually here because there's no logged-in request yet —
  // we just looked up the tenant by slug and know its ID.
  let user = null;
  if (tenant) {
    user = await runWithTenant({ tenantId: tenant._id }, async () => {
      // tenantId is auto-injected by tenantPlugin; we don't pass it
      return User.findOne({ email });
    });
  }

  // 3. Always run bcrypt.compare to prevent timing attacks.
  // If user doesn't exist or is inactive, compare against a dummy hash.
  const hashToCompare = (user && user.isActive) ? user.passwordHash : DUMMY_HASH;
  const passwordMatch = await bcrypt.compare(password, hashToCompare);

  // 4. If any check failed, return the SAME generic message.
  // This prevents attackers from discovering which companies/emails exist.
  if (!tenant || !user || !user.isActive || !passwordMatch) {
    throw new AppError('Invalid credentials', 401);
  }

  // 5. Fetch the role to get current permissions (inside tenant context)
  const role = await runWithTenant({ tenantId: tenant._id }, async () => {
    return Role.findById(user.roleId).lean();
  });
  if (!role) {
    throw new AppError('Invalid credentials', 401);
  }

  // 6. Issue tokens and store refresh token hash (inside tenant context)
  const tokens = await runWithTenant({ tenantId: tenant._id }, async () => {
    return issueAndStoreTokens(user, role.permissions);
  });

  // 7. Return tokens + minimal user object (no password hash)
  return {
    ...tokens,
    user: {
      id: user._id,
      name: user.name,
      email: user.email,
      role: role.name,
    },
  };
}

Line-by-line Explanation:

  1. export async function login({ companySlug, email, password }) {: Defines the asynchronous login function, accepting companySlug, email, and password as arguments.
  2. const tenant = await runUnscoped( ... );: Company Lookup (Unscoped). This line looks up the tenant using the provided companySlug. It uses runUnscoped because the Tenant model itself is not tenant-scoped (it's the top level of the multi-tenant hierarchy), meaning it doesn't automatically filter by tenantId.
  3. let user = null; if (tenant) { user = await runWithTenant({ tenantId: tenant._id }, async () => { return User.findOne({ email }); }); }: User Lookup Inside Tenant Context. If a tenant is found, this block looks for the user. Crucially, it uses runWithTenant to establish the context of the identified tenant (tenant._id). This ensures that the User.findOne({ email }) query is automatically scoped by the tenantPlugin to only search within that specific tenant, preventing users from one company logging into another.
  4. const hashToCompare = (user && user.isActive) ? user.passwordHash : DUMMY_HASH; const passwordMatch = await bcrypt.compare(password, hashToCompare);: Dummy Bcrypt Compare for Timing Attack Protection. To prevent timing attacks (where an attacker could infer valid usernames/companies by measuring response times), bcrypt.compare is always executed. If no tenant is found, no user exists, or the user is inactive, the password is compared against a DUMMY_HASH. This ensures the cryptographic comparison takes a consistent amount of time regardless of whether the user or company exists, thus preventing enumeration.
  5. if (!tenant || !user || !user.isActive || !passwordMatch) { throw new AppError('Invalid credentials', 401); }: Generic Error Message. If any authentication check fails (invalid tenant, user not found, inactive user, or incorrect password), a generic "Invalid credentials" error is returned. This is another critical security measure to prevent attackers from gaining information about the system's state (e.g., distinguishing between "company not found" vs. "user not found" vs. "incorrect password").
  6. const role = await runWithTenant({ tenantId: tenant._id }, async () => { return Role.findById(user.roleId).lean(); });: Fetches the user's role and associated permissions within the established tenant context.
  7. const tokens = await runWithTenant({ tenantId: tenant._id }, async () => { return issueAndStoreTokens(user, role.permissions); });: Issues new access and refresh tokens, and stores the hash of the refresh token, all within the tenant's context.
  8. return { ...tokens, user: { id: user._id, name: user.name, email: user.email, role: role.name, }, };: Returns the newly issued tokens and a minimal user object (without sensitive information like password hashes).

Timing Attack Prevention

The use of DUMMY_HASH and a generic error message for all login failures is crucial for preventing timing attacks and user enumeration. Attackers cannot discern valid company slugs or email addresses based on varying response times or error messages.
