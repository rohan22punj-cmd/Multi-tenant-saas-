    Why Isolation Tests Use TWO Real Companies Against Real In-Memory MongoDB

    No mocks. tests/tenantIsolation.test.js creates two actual tenants (Company A and Company B) with real users, roles, and documents in mongodb-memory-server. Here's why:

    1. Mocks Cannot Prove Isolation

    // MOCK APPROACH (what we DON'T do):
jest.mock('../src/models/User');
User.find.mockResolvedValue([{ tenantId: 'A' }]);
// This only proves the mock returns what we told it to.
// It proves NOTHING about the actual tenant plugin behavior.

    A mock returns exactly what you program it to return. It cannot catch bugs in the plugin's applyTenantFilter logic, the $geoNear error, the forced overwrite behavior, or the runUnscoped escape hatch.

    2. Real MongoDB Catches Real Bugs

    // tests/tenantIsolation.test.js (lines 111-117) — REAL test

it('inside A context, findOne with explicit B tenantId filter returns null (forced overwrite)', async () => {
  const user = await runWithTenant({ tenantId: tenantA._id }, async () =>
    User.findOne({ tenantId: tenantB._id, email: 'bob@b.com' }).lean()
  );
  expect(user).toBeNull();
});

    This test caught a real bug during development: the plugin was originally rewriting the filter instead of force-overwriting. The rewrite would turn updateMany({ tenantId: B }) into updateMany({ tenantId: A }) — matching ALL of Company A's documents. The forced overwrite (setting _id: { $in: [] }) makes the operation a no-op instead.

    3. mongodb-memory-server Is a Real MongoDB

    • Runs actual MongoDB binary in-memory (not a mock, not an approximation)
    • Supports transactions, indexes, aggregations, $geoNear, TTL indexes
    • Each test suite gets a fresh database via clearTestDB() in beforeEach
    • No external dependency — runs in CI without a MongoDB server

    4. The Test Helper Pattern

    // tests/tenantIsolation.test.js (lines 50-70)

async function createTenant(name, slug) {
  return runUnscoped(`test: create tenant ${name}`, () => Tenant.create({ name, slug }));
}

async function createRoleInContext(tenantId, name, permissions) {
  return runWithTenant({ tenantId }, async () => Role.create({ name, permissions, isSystemRole: true }));
}

async function createUserInContext(tenantId, name, email, passwordHash, roleId) {
  return runWithTenant({ tenantId }, async () => User.create({
    name, email, passwordHash, roleId
  }));
}

    runWithTenant and runUnscoped are the SAME functions used by the application. Tests exercise the exact same code paths.

    5. HTTP-Level Concurrency Test (20+ Mixed Requests)

    // tests/tenantIsolation.test.js (lines 459-509)

it('20+ mixed concurrent requests to /api/me never mix tenant data', async () => {
  const requests = [];

  for (let i = 0; i < 10; i++) {
    requests.push(request(app).get('/api/me').set('Authorization', `Bearer ${tokenA}`));
  }
  for (let i = 0; i < 10; i++) {
    requests.push(request(app).get('/api/me').set('Authorization', `Bearer ${tokenB}`));
  }

  const responses = await Promise.all(requests);

  // Verify all succeeded
  responses.forEach(res => expect(res.status).toBe(200));

  // Verify A's requests all see A's tenantId
  const aResponses = responses.slice(0, 10);
  aResponses.forEach(res => expect(res.body.data.tenantId).toBe(aTenantId));

  // Verify B's requests all see B's tenantId
  const bResponses = responses.slice(10, 20);
  bResponses.forEach(res => expect(res.body.data.tenantId).toBe(bTenantId));

  expect(aTenantId).not.toBe(bTenantId);
  // Verify no mixing
  aResponses.forEach(res => expect(res.body.data.tenantId).toBe(aTenantId));
  bResponses.forEach(res => expect(res.body.data.tenantId).toBe(bTenantId));
});

    This test runs the FULL HTTP stack: Express → protect.js → AsyncLocalStorage → /api/me handler. It proves the context doesn't leak between concurrent requests in the same event loop.

    What Is NOT Tested

    The following behaviors are explicitly NOT covered by the test suite. They are known gaps.

    1. Stripe Webhooks — PLANNED, Not Built

    • No webhook endpoint exists in the codebase
    • No signature verification tests
    • No idempotency tests (Redis SET NX or MongoDB unique index)
    • No plan sync tests (Tenant plan update from Stripe events)

    See Part 4i for the planned design.

    2. Raw MongoDB Driver Calls

    • No tests for Model.collection.find(), Model.collection.insertOne(), mongoose.connection.db
    • These bypass the tenant plugin entirely (see Part 6, Gap #2)
    • No test proves they are blocked or detected

    3. Multi-Process Distributed Locks

    • withTenantLock in userController.js is only tested in a single process
    • No test runs multiple Node processes behind a load balancer
    • The concurrent demote test (changeRole.test.js lines 389-436) only proves in-process serialization works
    • Redis SET NX distributed lock is PLANNED but not implemented or tested

    4. $lookup / $unionWith Cross-Collection Isolation

    • No aggregation tests with $lookup or $unionWith
    • The tenant plugin does NOT auto-scope sub-pipelines (see Part 6, Gap #1)
    • No test proves data leak or proves manual $match works

    5. Token Revocation / Blocklist

    • 15-minute access token window is documented but not tested as a security property
    • No test verifies a deactivated user's token works for up to 15 minutes
    • Redis blocklist is PLANNED but not implemented

    6. Bulk Operations (bulkWrite) with runUnscoped

    • Tests verify bulkWrite throws when scoped (tenantIsolation.test.js lines 373-379)
    • Tests verify bulkWrite works inside runUnscoped (lines 386-395)
    • NO test verifies that a developer using runUnscoped for bulkWrite correctly scopes their operations manually

    7. Estimated Document Count

    • Tests verify estimatedDocumentCount throws when scoped (tenantIsolation.test.js lines 367-371)
    • Tests verify it works inside runUnscoped (lines 381-384)
    • NO test for the alternative countDocuments performance characteristics

    8. Email Delivery / Invite Links

    • Invite flow is tested (rbac.test.js, userDeactivate.test.js)
    • But actual email sending, link generation, and token hashing are not integration tested
    • Accept-invite endpoint tested but not the full email → click → accept flow
