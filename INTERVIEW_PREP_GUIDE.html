Section 1: System Overview & Architecture

The Core Problem

You're building software that multiple companies use — like Slack or Trello. Each company needs their own workspace where data is completely invisible to others. Three architectural choices:

❌ Database Per Tenant

Cost: 1,000 companies × $15/month = $15,000/month

Isolation: Perfect (physical separation)

Complexity: Database routing, 1,000 migrations

Wins: Banking, healthcare (legally required), huge enterprise customers ($50k+/year)

⚠️ Schema Per Tenant

Cost: One database, schemas × tenants

Isolation: Good (logical separation)

Complexity: Medium — schema routing

Wins: Mid-market SaaS (50-500 tenants)

✅ Shared DB + tenantId (Our Choice)

Cost: One cluster ($25/month → thousands of tenants)

Isolation: Code-enforced (Mongoose plugin)

Complexity: Lowest — one migration, simple pooling

Wins: Startups, SMB SaaS, most modern apps (10 to 10,000 tenants)

Why Shared Database

Lowest cost, simplest operations, and isolation risk is manageable with the right code patterns. Every query gets tenantId force-injected by a plugin. 95% isolation benefit at 5% of the cost.

Request Flow: User Lists Their Projects

  1. HTTP arrives: GET /api/projects + Authorization: Bearer eyJ...
  2. protect.js middleware:
    • Extracts & verifies JWT signature
    • Decodes: { userId, tenantId, roleId, permissions }
    • Sets req.user
    • Wraps rest in runWithTenant({ tenantId, userId }, callback)
  3. AsyncLocalStorage: Creates invisible async context that follows every operation
  4. requirePermission: Checks req.user.permissions includes 'project:read' → 403 if missing
  5. Controller: await Project.find({})
  6. Mongoose plugin intercepts: Calls getTenantId(), force-overwrites filter: { tenantId: ObjectId("...") }
  7. MongoDB: db.projects.find({ tenantId: ObjectId("...") })
  8. Response: Only that company's projects

Key Insight

Isolation lives in the data layer, not controllers. Controllers write Project.find({}) as if they own the whole database. Plugin filters everything. Prevents 99% of isolation bugs.

Q: "Why shared database architecture?"

Answer: I chose shared database with tenantId because it's the most cost-effective and operationally simple for multi-tenant SaaS. One MongoDB cluster serves thousands of companies at a fraction of the cost. Isolation risk is managed through a Mongoose plugin that force-injects tenantId on every query and throws outside tenant context. This scales from 10 to 10,000 tenants without architectural rewrites.

Section 3: Signup — Creating Tenants & Users

1. WHAT We Built

POST /api/auth/signup endpoint that creates a Tenant, two default Roles (admin, member), and the first admin User in one atomic operation.

2. WHY This Comes Now

After foundation but before login. You need tenants and users to exist before anyone can log in. This is the entry point to the system.

3. THE PROBLEM

❌ Without Proper Signup

Problem 1: Partial Creation

// Create tenant
const tenant = await Tenant.create({ name: 'Acme' });

// Server crashes here — tenant exists but no admin!
// Now the company is orphaned

const adminRole = await Role.create({ ... });

Problem 2: Slug Collisions

// Two companies named "Acme Corp"
// Both get slug "acme-corp"
// Second signup overwrites first tenant's data!

Problem 3: Plain Text Passwords

await User.create({
  email: 'admin@acme.com',
  password: 'SecureP@ss123'  // ❌ Stored in plain text!
});

4. HOW It Works

Signup Flow (7 Steps)

export async function signup({ companyName, adminName, email, password }) {
  // 1. Generate URL-safe slug
  const slug = slugify(companyName);  // "Acme Corp" → "acme-corp"

  // 2. Check for duplicate slug (UNSCOPED — Tenant has no tenantId)
  const existing = await runUnscoped(
    'signup: check duplicate slug',
    () => Tenant.findOne({ slug })
  );
  if (existing) throw new AppError('Slug already exists', 409);

  // 3. Create tenant
  const tenant = await runUnscoped(
    'signup: create tenant',
    () => Tenant.create({ name: companyName, slug })
  );

  // 4-7. INSIDE tenant context, create roles + user
  return runWithTenant({ tenantId: tenant._id }, async () => {
    // 4. Create default roles
    const [adminRole] = await Role.create([
      { name: 'admin', permissions: ALL_PERMISSIONS, isSystemRole: true },
      { name: 'member', permissions: MEMBER_PERMISSIONS, isSystemRole: true }
    ]);

    // 5. Hash password with bcrypt (salt rounds = 12)
    const passwordHash = await bcrypt.hash(password, 12);

    // 6. Create first user (tenantId auto-stamped by plugin)
    const user = await User.create({
      name: adminName,
      email,
      passwordHash,
      roleId: adminRole._id
    });

    // 7. Issue JWT tokens
    const tokens = await issueAndStoreTokens(user, adminRole.permissions);

    return { ...tokens, tenant, user };
  });
}

Why runUnscoped for Tenant Operations?

// Tenant model has NO tenantId field (it IS the tenant)
// Calling Tenant.findOne() inside a scoped context would:
// 1. Plugin calls getTenantId()
// 2. Tries to filter: { tenantId: ... }
// 3. Field doesn't exist on Tenant schema → error!

// Solution: runUnscoped temporarily disables tenant filtering
await runUnscoped('reason', () => Tenant.findOne({ slug }))

5. THE ALTERNATIVES

Option 1: Manual Transaction

Pros: Explicit MongoDB transaction, atomic rollback

Cons: Requires replica set, complex code, performance overhead

Why not: For local dev and small scale, try/catch + cleanup is simpler

Option 2: Separate Signup Steps

Pros: User creates tenant first, then gets invited

Cons: Two-step UX, orphaned tenants if user doesn't finish

Why not: One-step signup is standard SaaS pattern

Option 3: Our Choice — Nested Context

Pros: Clean code, automatic tenantId stamping, one atomic operation

Cons: Requires understanding runWithTenant + runUnscoped

Why: Best balance of simplicity and safety

6. THE WEAK SPOTS

  • Slug collision race: Two signups with same name at exact same millisecond could both pass the duplicate check. Fix: unique index on Tenant.slug + handle duplicate key error
  • Email verification: We don't verify emails yet. Production needs email confirmation before activating account
  • Password strength: We accept any password. Add zxcvbn library or password rules
  • Rate limiting: One IP could spam signups. We add this next (Section 4)

7. THE INTERVIEW QUESTION

Q: "How does your signup process ensure data consistency when creating multiple related documents?"

Answer: Signup creates a Tenant, two Roles, and a User in one flow. I use runWithTenant to establish tenant context after creating the Tenant, which allows the Mongoose plugin to automatically stamp tenantId on Roles and User. If any step fails, the error bubbles up and the HTTP transaction fails before committing. For the Tenant lookup (checking duplicate slugs), I use runUnscoped because Tenant has no tenantId field. The key is that tenant context is established immediately after Tenant creation, so all subsequent documents are properly scoped. In production, I'd add a unique index on Tenant.slug and handle duplicate key errors for bulletproof race condition protection.

Section 16: 15 Hardest Interview Questions

1. "Walk me through exactly what happens when a user makes a request from their browser to your API. Cover every middleware, database call, and isolation check."

Answer: Request hits Express with Authorization header containing JWT. First, protect.js middleware extracts the token, verifies signature with ACCESS_SECRET, decodes payload to get userId, tenantId, roleId, and permissions array. It sets req.user with these values, then wraps the downstream in runWithTenant which stores the tenant context in AsyncLocalStorage. Next, requirePermission middleware checks if the needed permission exists in req.user.permissions array — returns 403 if missing. Controller calls service layer which queries Mongoose. Here's where isolation happens: the tenantPlugin's pre-hook on every query method calls getTenantId() from AsyncLocalStorage and force-overwrites the filter with the correct tenantId. Even if a controller tried to pass a different tenantId, it gets replaced. MongoDB executes the query filtered by that tenantId, ensuring complete isolation. Response flows back through controllers with only that tenant's data.

2. "Your Mongoose plugin forces tenantId on every query. What happens with aggregation pipelines, populate, and other complex operations?"

Answer: The plugin hooks pre('aggregate') and injects a $match stage at pipeline position 0 with the tenantId. For populate, Mongoose internally runs separate queries for referenced documents, and those queries also go through the plugin's pre-hooks, so they're automatically filtered. The one exception is $geoNear which MUST be first in a pipeline — we detect that and throw an error telling the developer to use runUnscoped with justification. For findOneAndUpdate, updateMany, deleteMany — these all have pre-hooks that inject tenantId into the filter before execution. bulkWrite is blocked entirely because it takes arbitrary operations that can't be safely auto-scoped. We force developers to use runUnscoped for that with explicit reasoning.

3. "How do you prevent privilege escalation in your invite system?"

Answer: When a user invites someone, they specify a roleId for the invitee. Before creating the invite, I fetch that role's permissions array and compare it against the inviter's permissions (from req.user.permissions in the JWT). I check if the target role has ANY permission the inviter doesn't have. If yes, return 403 Forbidden. This prevents a low-privilege user from inviting someone with admin powers. The same check applies when changing a user's role later — you can only assign roles with permissions you yourself possess. This is enforced at the API level, and the JWT permissions come from the database at login time, so there's no way to forge higher permissions without compromising the JWT secret.

4. "Explain refresh token rotation and reuse detection. Why is it important?"

Answer: We store a SHA-256 hash of the refresh token in the database, never the raw token. When /refresh is called, we hash the incoming token and compare hashes. If it matches, we issue NEW access and refresh tokens, replacing the stored hash — that's rotation. If it DOESN'T match, someone is replaying an old token that was already rotated, which means either the token was stolen or the user's token storage is compromised. We immediately wipe the stored hash to null, killing ALL sessions for that user. This is reuse detection — a security tripwire. It's important because stolen refresh tokens can be used indefinitely (7 day expiry), but rotation limits the window and reuse detection catches the attack, forcing re-authentication.

5. "Why do you use AsyncLocalStorage instead of just passing tenantId through function parameters?"

Answer: Passing tenantId as a parameter through every function would require changing the signature of every service method, utility function, and Mongoose plugin hook. That's hundreds of places. AsyncLocalStorage creates an invisible context that automatically propagates through async operations — promises, callbacks, setTimeout, everything. The Mongoose plugin can call getTenantId() without the controller knowing anything about it. This keeps business logic clean and makes tenant isolation a cross-cutting concern handled at the framework level. The alternative is passing tenantId explicitly, which is error-prone because forgetting it once creates a data leak. AsyncLocalStorage + throwing on missing context makes leaks impossible.

6. "How do you prevent timing attacks in your login endpoint?"

Answer: Timing attacks let attackers discover which emails exist by measuring response time. If user doesn't exist, we return fast. If they exist but wrong password, bcrypt takes 100ms. Attacker learns email validity. I prevent this by ALWAYS running bcrypt.compare even when the user doesn't exist — I compare against a dummy hash that takes the same time. Then I return the same generic "Invalid credentials" message for every failure: wrong company, wrong email, wrong password, or deactivated user. All return 401 with identical messages and identical timing. No information leaks.

7. "Your access tokens don't check the database on every request. What's the security trade-off?"

Answer: JWTs are stateless — I verify signature and expiry, then trust the payload. This means if I deactivate a user or change their role, their current access token remains valid for up to 15 minutes until it expires. That's the trade-off for performance — no database round-trip on every request. I accept it because: (1) 15 minutes is short enough for most use cases, (2) on deactivation, I wipe their refresh token so they can't get a NEW access token, cutting off future sessions immediately, and (3) a revocation list in Redis (which I haven't built yet) can provide instant revocation if needed, at the cost of a Redis check on every request.

8. "Walk me through your Stripe webhook handling. How do you ensure exactly-once processing?"

Answer: (PLANNED FEATURE) Stripe sends the same webhook multiple times if we don't respond quickly enough. To ensure exactly-once processing: (1) Verify webhook signature using Stripe's library and the raw request body — this proves it came from Stripe. (2) Extract event ID from the webhook payload. (3) Redis SET NX with key "stripe:event:{id}" and TTL of 24 hours. SET NX only succeeds if the key doesn't exist. (4) If SET NX returns false, we already processed this event — return 200 immediately without processing again. (5) If SET NX succeeds, process the event (update subscription, credit projects, etc.) and commit to database. (6) Return 200 to Stripe. If the server crashes during step 5, Redis key doesn't exist, so retry will process it. If we crash after step 5 but before responding, Stripe retries, but Redis key exists, so we skip processing and just return 200. This guarantees exactly-once.

9. "How would you implement row-level security for projects where users can only see projects they're assigned to?"

Answer: I'd add a Project schema field: assignedUsers (array of ObjectIds referencing User). The controller gets userId from req.user.userId. Then Project.find({ assignedUsers: userId }). But this has a problem — the tenant plugin already filters by tenantId, and adding assignedUsers creates an AND condition. So the query becomes: find projects in my tenant AND where I'm assigned. This is correct. For "all projects in tenant" (admin view), I'd add a permission like 'project:read:all'. If user has that, query is Project.find({}) with only tenantId filtering. If they don't, query is Project.find({ assignedUsers: userId }). This keeps tenant isolation (plugin handles it) while adding user-level access control in the controller.

10. "What happens if someone calls mongoose.connection.collection('users').find() to bypass your plugin?"

Answer: That's using the raw MongoDB driver, which completely bypasses Mongoose and therefore bypasses the plugin. It would return ALL users across ALL tenants — a catastrophic data leak. My defense: (1) Code review — never allow raw driver calls. (2) Linting rule — ban mongoose.connection.collection usage in code. (3) The principle of least privilege — developers should never need raw driver access in application code. Only migrations and admin scripts use it, and those run outside normal request context. If we absolutely need raw queries, wrap them in runUnscoped with a logged justification, and manually add tenantId filtering. There's no runtime defense against intentionally bypassing the framework, which is why code review and tooling are critical.

11. "How do you handle background jobs that need to access tenant data?"

Answer: Background jobs (cron, queues) don't have req.user from HTTP requests, so no automatic tenant context. Options: (1) Pass tenantId as job payload when queueing. When processing, call runWithTenant({ tenantId }, async () => { ... }) to establish context, then use normal Mongoose queries. (2) For jobs that process multiple tenants, loop through Tenant.find() (unscoped), and for each tenant, run the job's logic inside runWithTenant. (3) For tenant-agnostic jobs (system maintenance), use runUnscoped with justification. The key is: NEVER run database queries in a background job without explicitly setting context via runWithTenant or runUnscoped. Make getTenantId() throw if called without context so missing context is caught immediately.

12. "Your system uses one MongoDB connection pool. How does that work with tenant isolation?"

Answer: MongoDB connection pooling is application-level, not tenant-level. One pool serves all tenants because we're using shared database architecture. Each connection can execute queries for any tenant — isolation happens at the QUERY level (tenantId filtering), not the CONNECTION level. This is a huge advantage: connection pooling is simple, we don't need tenant-specific pools or routing logic, and we get efficient connection reuse. The pool size is configured based on total load, not per-tenant. For a database-per-tenant architecture, we'd need routing logic and possibly separate pools per tenant, which is much more complex.

13. "How do you test tenant isolation? What's your testing strategy?"

Answer: I use mongodb-memory-server for integration tests — an in-memory MongoDB instance per test suite. Each test: (1) Signs up TWO companies (Tenant A and Tenant B). (2) Creates users in each tenant. (3) Logs in as Tenant A user, creates a project. (4) Logs in as Tenant B user, tries to fetch Tenant A's project by ID. (5) Asserts 404 Not Found — the plugin filtered it out. Also test: aggregate queries, populate, updateMany, and that accessing data outside runWithTenant throws an error. I DON'T mock the database because mocks can't catch isolation bugs. Real MongoDB queries going through the real plugin is the only way to verify isolation. Tests run in ~2 seconds because in-memory DB is fast.

14. "Explain the difference between roles and permissions. Why check permissions in code, not role names?"

Answer: A role is a named collection of permissions that belongs to a tenant (e.g., "admin", "editor", "viewer"). Permissions are atomic capabilities like 'project:delete', 'user:invite'. The critical rule: CODE NEVER CHECKS ROLE NAMES. We check permissions. Why? Because tenants can create custom roles. If I write if (user.role === 'admin'), that breaks when a tenant makes a custom "manager" role with the same permissions. But if I write requirePermission('project:delete'), it works for any role that has that permission. The JWT payload includes the permissions array, so the check is fast (no database call). Roles are UI/organizational — they group permissions for easier assignment. Permissions are the source of truth for access control.

15. "What's the biggest security risk in your current implementation and how would you fix it?"

Answer: The biggest risk is that access tokens don't check user.isActive on every request due to JWT statelessness. A deactivated user keeps access for up to 15 minutes. In a high-security context, that's unacceptable. The fix: maintain a Redis blocklist of deactivated users. Key: "blocked:user:{userId}", value: "1", TTL: 15 minutes. On deactivation, set that key. In protect.js middleware, after verifying JWT, check if (await redis.get(`blocked:user:${userId}`)). If key exists, return 401 immediately. This adds one Redis call per request (~1ms latency), but gives instant revocation. Trade-off is performance vs security, and for most apps, 15-minute grace period is acceptable. For banking/healthcare, add the blocklist.

  2. Multi-Region Deployment

  3. Real-Time Collaboration

    Add WebSocket support for live project updates. When user A edits a task, user B sees it instantly. Requires Socket.io + Redis pub/sub.

  4. Two-Factor Authentication

    Add TOTP (Google Authenticator) support. Require 2FA for admin roles. Store recovery codes hashed in database.

Performance Optimizations

  • Query result caching: Cache frequently-accessed data in Redis with tenant-specific keys. Invalidate on writes.
  • Database indexing: Add compound indexes on frequently queried fields. Monitor slow query log.
  • Connection pooling tuning: Increase pool size based on load testing. Monitor pool exhaustion.
  • API response pagination: Return max 100 items per page. Add cursor-based pagination for large result sets.

Code Quality

  • E2E tests: Add Playwright tests for critical flows (signup → create project → invite user).
  • Load testing: Use k6 to test 1000 req/sec. Find bottlenecks before production.
