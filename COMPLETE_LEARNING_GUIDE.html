What You Built

A production-grade backend where many companies (tenants) share one server and one MongoDB database, with complete data isolation between companies. Inside each company, users have roles that grant specific permissions. The system handles Stripe payments through webhooks with exactly-once processing, and includes a mini project-management tool as the demo app.

Stack: Node.js + Express (ES modules), MongoDB + Mongoose (shared database with tenantId), Redis (idempotency), JWT (access + refresh), Stripe webhooks, Jest + Supertest, Docker Compose

Section 1: System Overview & Architecture

The Core Problem This Project Solves

Imagine you're building software that multiple companies will use — like Slack, Trello, or Notion. Each company needs their own workspace where their data is completely invisible to every other company. You have three architectural choices:

❌ Separate Database Per Tenant

Cost: If you have 1,000 companies and each has a small MongoDB instance ($15/month), you're paying $15,000/month.

Isolation: Perfect — data physically separated.

Complexity: You need database routing logic, migrations across 1,000 databases, and connection pool management.

When it wins: Highly regulated industries (banking, healthcare) where physical separation is legally required, or when tenants are huge enterprises paying $50k+/year each.

⚠️ Separate Schema Per Tenant

Cost: One database, but Postgres schemas or MongoDB collections multiplied by tenant count.

Isolation: Good — logical separation within one database.

Complexity: Medium — schema routing, migrations harder than single-schema.

When it wins: Mid-market SaaS (50-500 tenants) where some isolation is valuable but full DB separation is overkill.

✅ Shared Database with tenantId (Our Choice)

Cost: One MongoDB cluster serves all tenants — from $25/month to thousands of companies.

Isolation: Enforced by code — every query filtered by tenantId automatically via Mongoose plugin.

Complexity: Lowest operational overhead. One migration runs once. Connection pooling is trivial.

When it wins: Startups, SMB SaaS, most modern applications. Scales from 10 to 10,000 tenants without architecture changes.

Why We Chose Shared Database

For a portfolio project and most real startups, shared database is the clear winner: lowest cost, simplest operations, and the isolation risk is manageable with the right code patterns. Every Mongoose query gets tenantId force-injected by a plugin that throws errors outside a tenant context. This gives us 95% of the isolation benefit at 5% of the cost.

How Data Flows Through One Request

Example: A user lists their company's projects
  1. HTTP Request arrives: GET /api/projects with Authorization: Bearer eyJhbG...
  2. protect.js middleware runs:
    • Extracts JWT from Authorization header
    • Verifies signature with ACCESS_SECRET
    • Decodes payload: { userId, tenantId, roleId, permissions: ['project:read', ...] }
    • Sets req.user with these values
    • Wraps the rest of the request in runWithTenant({ tenantId, userId }, callback)
  3. AsyncLocalStorage stores tenant context:
    • runWithTenant calls asyncLocalStorage.run(context, callback)
    • This creates an invisible "async context" that follows every async operation downstream
    • Any code that runs later in this request (controllers, services, Mongoose) can call getTenantId()
  4. requirePermission middleware runs:
    • Checks if req.user.permissions includes 'project:read'
    • Returns 403 if missing, otherwise continues
  5. Controller calls service: 
    const projects = await Project.find({});
  6. Mongoose plugin intercepts the query:
    • The pre('find') hook fires
    • Calls getTenantId() from AsyncLocalStorage
    • Force-overwrites the filter: { tenantId: ObjectId("...") }
    • Even if the controller tried to pass a different tenantId, it gets replaced
  7. MongoDB query executes: 
    db.projects.find({ tenantId: ObjectId("507f1f77bcf86cd799439011") })
  8. Response returns only that company's projects

The Key Insight

Isolation lives in the data layer, not the controller layer. Controllers never touch tenantId. They write queries as if they own the whole database (Project.find({})), and the Mongoose plugin automatically filters everything. This prevents 99% of isolation bugs because there's no manual filtering to forget.

What Makes This Production-Grade

  • Security: JWT tokens, bcrypt hashing, rate limiting, timing attack prevention, refresh token rotation with reuse detection
  • Isolation: tenantId force-injected on every query, throws outside context, prevents cross-tenant leaks
  • RBAC: Permissions (not role names) checked in code, privilege escalation rules on invite/role change
  • Observability: Structured logging with request IDs, every log line correlates to one request
  • Idempotency: Stripe webhooks processed exactly once via Redis SET NX
  • Testing: In-memory MongoDB, full integration tests, no mocks for database
  • Deployment: Docker Compose for local dev, ready for production deployment
Interview Question: "Why did you choose a shared database architecture?"

My Answer: I chose shared database with tenantId because it's the most cost-effective and operationally simple approach for a multi-tenant SaaS. One MongoDB cluster can serve thousands of companies at a fraction of the cost of separate databases. The isolation risk is managed through a Mongoose plugin that force-injects tenantId on every query and throws errors if called outside a tenant context. This gives us strong isolation guarantees without the operational burden of managing thousands of database instances or running migrations across all of them. For a startup or portfolio project, this is the architecture that scales from 10 to 10,000 tenants without needing a rewrite.

Section 2: Foundation — Folder Structure & Error Handling

1. WHAT We Built

A clean folder structure following MVC pattern, plus a central error handler that catches all errors and returns consistent JSON responses.

2. WHY This Comes First

You cannot build anything without knowing where files go. The folder structure is the foundation — every other feature builds on top of it. The error handler comes first because once you start writing controllers and services, you need a consistent way to handle failures.

3. THE PROBLEM It Solves

❌ Bad Case Without Central Error Handler
// Controller 1
try {
  await doSomething();
} catch (err) {
  res.status(500).json({ error: err.message });
}

// Controller 2
try {
  await doSomethingElse();
} catch (err) {
  res.status(400).send(err.toString());
}

// Controller 3
try {
  await yetAnother();
} catch (err) {
  console.error(err);
  res.status(500).json({ msg: 'failed' });
}

Problems:

  • Inconsistent error response shapes: { error } vs { msg }
  • Status codes scattered everywhere
  • Stack traces might leak to production
  • No central place to log errors

4. HOW It Works Inside

Folder Structure

src/
├── config/        # env vars, db connection, logger setup
├── models/        # Mongoose schemas
├── middleware/    # protect.js, requirePermission, etc.
├── controllers/   # HTTP layer — reads req, calls service, sends res
├── services/      # Business logic — NO req/res knowledge
├── routes/        # URL → middleware → controller mapping
├── utils/         # helpers (AppError, asyncHandler, tokens)
├── plugins/       # tenantPlugin.js
└── server.js      # Entry point

AppError Class

class AppError extends Error {
  constructor(message, statusCode) {
    super(message);
    this.statusCode = statusCode;
    this.isOperational = true;  // safe to expose to client
    Error.captureStackTrace(this, this.constructor);
  }
}

Key idea: isOperational: true marks errors we expect (user not found, invalid credentials). These are safe to show to the client. Unexpected errors (database connection failed, out of memory) have isOperational: false and get a generic "Internal Server Error" message.

Central Error Handler

const errorHandler = (err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  const message = err.isOperational ? err.message : 'Internal Server Error';

  // Log non-operational errors with stack trace
  if (!err.isOperational) {
    console.error(err.stack);
  }

  res.status(statusCode).json({
    status: 'error',
    statusCode,
    message,
  });
};

// In app.js, MUST be the last middleware
app.use(errorHandler);

asyncHandler Wrapper

const asyncHandler = (fn) => (req, res, next) => {
  Promise.resolve(fn(req, res, next)).catch(next);
};

// Usage in controller
export const getProjects = asyncHandler(async (req, res) => {
  const projects = await Project.find({});
  res.json({ data: projects });

  // If Project.find() throws, asyncHandler catches it
  // and passes it to errorHandler
});

5. THE ALTERNATIVES

Option 1: Try/Catch in Every Controller

Pros: Explicit error handling, no magic

Cons: Massive code duplication, easy to forget, inconsistent responses

Why we didn't pick it: DRY principle — repeating try/catch 50 times is maintenance hell

Option 2: Domain-Specific Error Classes

Pros: UserNotFoundError, InvalidCredentialsError — very explicit

Cons: Need 20+ error classes, overhead for simple cases

Why we didn't pick it: AppError with a message and status code is simpler and just as clear

Option 3: Our Choice — AppError + asyncHandler

Pros: One place for error formatting, controllers stay clean, consistent responses

Cons: Requires wrapping async handlers (small overhead)

Why we picked it: Best balance of simplicity and consistency

6. THE WEAK SPOTS

  • Stack traces in production: We suppress them for non-operational errors, but a better solution is a proper error tracking service (Sentry, Rollbar) that captures full context without exposing it to users
  • Error codes: We use HTTP status codes, but larger systems add machine-readable error codes (USER_NOT_FOUND, RATE_LIMIT_EXCEEDED) for client-side internationalization
  • Async errors outside Express: Background jobs, event emitters, and streams need separate error handling

7. THE INTERVIEW QUESTION

"How do you handle errors in your Express app?"

My Answer: I use a central error handler that's the last middleware in the chain. All errors flow there through Express's next(err). I have a custom AppError class that marks operational errors (like "user not found") as safe to expose to the client. Unexpected errors like database failures get a generic message to avoid leaking internals. Controllers are wrapped in asyncHandler so thrown errors from async functions automatically reach the error handler. This keeps error responses consistent across the entire API and gives me one place to add logging, monitoring, or error tracking later.
